YOpen Y-finder

Y-finder design notes

How the data guide was built and tested, what it costs, and what it would take to run it at the Yale Center for Geospatial Solutions.

Huan Ning, November 2026. Y-finder is an independent prototype for the YCGS interview, not a Yale service.

The question it answers

YCGS receives more requests than its consultants can take: a student or a faculty member wants geospatial data for a study and does not know where to start. The first consult usually settles three things: what the study is really about, where and when it takes place, and which of the many candidate datasets fit. Y-finder does that first consult at any hour and hands the person on with a one-page guide. It is not a catalog with a search box, and it is not a chatbot that recommends from memory.

How it works

Y-finder follows the tri-projection used in Research Architect: real world, influence graph, scope, data.

  1. Frame. The agent turns the question into an influence graph: the outcome, the factors that drive, mediate or confound it, and a measurable observable for each. The user sees which factors are core and which have data.
  2. Scope. Place (geocoded, with the named boundary preferred over a point), years, the detail needed and the unit of analysis. Defaults the agent chose are marked and can be edited; every fit label is recomputed at once, without a model call.
  3. Data. Catalog search over 3,126 cards (116 curated by hand with Yale access routes; Planetary Computer, Earth Engine and its community catalog, GeoLibre's collections, World Bank indicators) and live searches of Yale and Harvard Dataverse, Yale Library GeoBlacklight, ArcGIS Online, Data.gov, US open data portals including Connecticut Open Data, Planetary Computer imagery and the web. Tables as well as maps, because many factors are measured by records and surveys.
  4. Fit. Rules, not the model, label each dataset for area, time, detail and access, with the reason in plain words. The overall label is the worst known one.
  5. Preview and insights. Online services are drawn on the map directly; otherwise a small slice (up to 100 MB) is downloaded for the session. While the user looks, Y-finder explores the previews along the graph (distributions, highest and lowest places, clustering, rank correlations after map joins) and reports findings with their caveats. Sources that need a person to download are tried by Y-finder's own browser, which reports what it found on the card.
  6. Hand-off. A printable data guide, the same layers in the GeoLibre web GIS, access handbooks in the Agent-Skill style, a consultation summary for YCGS staff, and opt-in follow-up searches.

What keeps it honest

  • Every recommended dataset must come from a search result in the same conversation. Anything else is marked "Not verified" and does not count as coverage of the graph.
  • Fit labels come from metadata and rules. The model never grades a dataset.
  • Web links are opened once; dead links are flagged and the model is told to replace them.
  • Previews show the variable the question asks for (race shares, residents under 18, tree canopy, the 1934 aerials), and say when a measure is a stand-in or a sample is uneven over time.
  • Exploration findings are computed by code. The model only picks the matching categories, checked against the real values, and writes a short reading of the computed numbers.
  • The answer opens with the data route, then the limits. A Yes or No under each answer records whether it helped.

What it costs

A consult turn reads about 50,000 tokens and writes about 2,000. At GPT-6.1 Terra list prices that is about 6 cents before caching; the estimate is shown under every answer. A full consult with previews and insights stays well under 50 cents, because the explorer calls the model only twice per run and only on computed numbers. Web search costs $0.75 per 1,000 queries. The app runs on one small virtual server without a GPU, next to Research Architect. Caps of 40 turns per address per hour and 600 per day protect the budget.

Running it at YCGS

YCGS would need a model key under Yale's agreement (the agent uses function tools only, so OpenAI, Azure OpenAI or another provider with the same interface will do), a server or container, the catalog harvest on a schedule, and staff time to curate the cards with Yale access routes. Yale CAS login can limit it to the Yale community. Questions go to the model vendor; nothing is stored beyond the six-hour session except the Yes or No feedback with the first 300 characters of the question. Licensed sources (Planet, Esri Business Analyst, PolicyMap, Dewey Data, L2, CoreLogic) are described with their access route and are never downloaded.

Where it fits: the YCGS request form (the consultation summary pastes into it), office hours (the data guide is the agenda), courses (the demo cases are worked examples), and GeoLibre (the same layers open there with one click).

The first six months

  1. An evaluation set from de-identified consult questions, reporting how often the right dataset is in the top five and how many guides a consultant would send as they are. The feedback under each answer feeds it.
  2. Yale's own holdings in full: Yale Library GeoBlacklight and Yale Dataverse, the Connecticut GIS Office and Connecticut Open Data through OGC API Records and CKAN; embedding search beside the keyword search.
  3. Handbooks reviewed by YCGS staff (22 drafts today), each with a run example.
  4. A consult queue: "Ask a YCGS consultant" posts the summary to staff instead of copy and paste.
  5. A monthly usage review: questions by school, datasets most recommended, gaps in the catalog.

What I would not build

  • A general chatbot about GIS. Y-finder answers one question: which data fits this study.
  • A new catalog. It reads the catalogs that exist and adds a thin layer of curation.
  • Analysis without a person. The previews and insights are leads; the study stays the researcher's.
  • Accounts and stored conversations. Nothing is kept beyond the session except the feedback.
